## Architecture

- Authoritative subjects: `CUSTOMER` from persisted `customerId` and
  `CHECKOUT_EMAIL` from the immutable normalized checkout email snapshot.
- Event type: `PAYMENT_CONFIRMED`.
- Inclusion semantics: trusted `FraudVelocityEventAuthorityPort` approval and a
  persisted order with `payment_status = CAPTURED` are required for event
  recording.
- Time source: `FraudRiskService` uses its injected `now()` clock. Velocity
  aggregate queries use trusted persisted `occurredAt` and explicit
  `evaluatedAt`.
- Windows: `PT15M`, `PT1H`, `PT24H`, using inclusive
  `[evaluatedAt - duration, evaluatedAt]` semantics.
- Aggregate strategy: PostgreSQL stores durable events and calculates
  count/amount aggregates from indexed rows.
- Customer/email transition: a single order may have one event per subject
  type. Idempotency prevents duplicate contribution within the same subject.
- Snapshot consistency: velocity subject lookup and aggregate reads occur in
  one PostgreSQL aggregate SQL statement for a fixed evaluation timestamp.
- Stale clearance: velocity facts participate in the `KS09_POLICY_V2`
  fingerprint, so aggregate changes invalidate older approvals until
  re-evaluation.

## Pseudonymization

- Email subject implemented: YES.
- Algorithm: versioned `v1:` HMAC-SHA-256 over the existing normalized checkout
  email.
- Dedicated secret behavior: a purpose-specific velocity correlation secret is
  required for checkout-email subjects.
- Raw email persistence: NO.
- Secret failure behavior: fail closed to unavailable velocity and fraud
  `REVIEW`.
- Rotation limitation: historical email correlation breaks if the secret
  changes and old approvals fail closed until re-evaluation; full rotation is
  future work.

## Fraud Policy

- Previous policy version: `KS09_POLICY_V1`.
- New policy version: `KS09_POLICY_V2` when velocity policy is configured.
- Velocity rules:
  - count review and deny thresholds;
  - amount-minor review and deny thresholds;
  - unavailable velocity signal review;
  - future timestamp anomaly review.
- Threshold model: typed policy configuration with validated windows, event
  type, currency, unique threshold identities, canonical positive windows,
  positive integer thresholds and frozen validated policy copies.
- Production thresholds approved: NO.
- Precedence: `DENY > REVIEW > ALLOW`.

## Persistence

Migration 021: YES.

Schema:

- `fraud_velocity_events`

Constraints:

- valid `PAYMENT_CONFIRMED` event type;
- valid `CUSTOMER` or `CHECKOUT_EMAIL` subject type;
- non-empty bounded safe subject key;
- non-negative amount minor;
- uppercase three-letter currency;
- non-null timestamps;
- FK to `keycore_orders`.

Indexes:

- unique `(event_type, order_id, subject_type)`;
- `(subject_type, subject_key, event_type, currency, occurred_at)`;
- `(order_id, occurred_at)`.

Idempotency/concurrency:

- duplicate logical event recording for the same order/event/subject is
  resolved by the unique index and returns idempotently.
- aggregate reads do not materialize counters and do not require global
  application serialization.

## Final Hardening Review

Findings fixed:

- High: orders without any supported velocity subject could be represented as
  available zero-velocity facts. Fix: no-subject derivation now returns
  unavailable and produces `VELOCITY_SIGNAL_UNAVAILABLE`.
- High: event timestamp and event issuance were caller-controlled. Fix:
  `FraudVelocityEventAuthorityPort` is required, production default fails
  closed, and timestamp validation rejects invalid/future/before-order events.
- High: PostgreSQL aggregate reads used multiple SELECTs under `READ COMMITTED`.
  Fix: all subject/window aggregates and future anomaly detection are now
  computed in one SQL statement.
- Medium: duplicate threshold definitions, zero thresholds and non-canonical
  window durations could be accepted. Fix: startup validation rejects them.
- Medium: caller mutation after service construction could alter nested
  threshold objects. Fix: validated policy is deep-copied and frozen.
- Medium: event recording audit counts could be ambiguous in partial
  guest-to-customer replay. Fix: return/audit `subjectEventCount` and
  `insertedEventCount`.
- Medium: malformed/incomplete/duplicate velocity aggregate facts could be
  evaluated as partial data. Fix: service validates subject uniqueness,
  aggregate completeness, duplicate aggregate identities and safe numeric
  bounds before applying velocity rules.
- Medium: missing checkout-email correlation secrets needed explicit
  persistence rollback coverage. Fix: PostgreSQL integration coverage now
  verifies secret-missing velocity recording returns unavailable and writes no
  partial event rows.

Migration 021 was amended because PR #33 is unmerged. Migration 022 was not
created.
