# KS-08-02 Implementation Report

## Summary

Implemented the customer registration and verified account-linking foundation as
a transport-neutral service. The implementation adds enumeration-safe
registration orchestration, hash-only email verification challenges, fake/local
verification delivery, rate-limit port, trusted verification authority
integration, authenticated verified external identity linking, fail-closed guest
order claim foundation, PostgreSQL persistence and safe inspect support.

No password authentication, OAuth login, WooCommerce login, production email
delivery, frontend UI, automatic login, account merge, email-only order claim,
Kinguin retrieval/purchase or live Stripe mutation was added.

- purpose `EMAIL_VERIFICATION`;
- SHA-256 token hash only;

- positive record version;

Rollback drops the challenge table.

## Registration Service Architecture

`CustomerRegistrationService` composes existing KS-07-06 identity primitives
instead of duplicating customer identity:

```text
register email -> normalize -> create/reuse UNVERIFIED customer -> issue challenge -> fake delivery
verify token -> hash -> consume challenge -> trusted EmailVerificationAuthorityPort -> mark verified
authenticated verified customer -> trusted CustomerIdentityBindingAuthorityPort -> identity binding
authenticated verified customer -> trusted GuestOrderClaimAuthorityPort -> OrderOwnershipBindingAuthorityPort
```

## Public Registration Outcome Semantics

Public registration returns `REGISTRATION_ACCEPTED` for both newly created and
existing normalized emails. It does not expose customer ID, existing-account
status, verification state, provider bindings or order ownership.

Malformed email and rate-limit denial return `REGISTRATION_DENIED` with a stable
reason code. Registration never accepts untrusted `VERIFIED` input and never
creates an authenticated principal or session.

## Customer Creation Behavior

Customer creation reuses `CustomerOrderIdentityService.createCustomer`.
Normalized email lookup semantics match KS-07-06: trim the address and lowercase
the domain only. Provider-specific Gmail dot stripping and plus stripping are
not implemented.

Concurrent same-email registration creates one customer identity; all public
responses remain enumeration-safe.

## Verification Challenge Schema

Challenges are customer-, purpose- and email-snapshot-bound. The persisted email
snapshot prevents a challenge issued for email A from verifying a later email B
on the same customer record.

## Token Format And Entropy

Raw verification tokens are generated with:

```text
randomBytes(32).toString("base64url")
```

This provides at least 256 bits of entropy.

## Token Hash Behavior

Only the SHA-256 token hash is persisted. Raw tokens are passed only to the
immediate `CustomerEmailVerificationDeliveryPort`. Raw tokens and token hashes
are excluded from audit metadata, inspect output and customer-facing surfaces.

## Challenge TTL

Default TTL:

```text
KEYCORE_CUSTOMER_EMAIL_VERIFICATION_TTL_MS=900000
```

Invalid TTL configuration fails closed.

## Challenge Reissue Policy

New challenge creation revokes older active challenges for the same customer,
purpose and normalized email snapshot. Older tokens then return the same public
`VERIFICATION_INVALID` result.

## Challenge Concurrency Strategy

PostgreSQL challenge creation uses a transaction and advisory lock for the
customer/purpose/email key. Token consumption uses transaction-scoped row
locking with `FOR UPDATE SKIP LOCKED` and a conditional consume update.

Ten concurrent consume attempts for one token can produce at most one
successful verification.

## Email Change Behavior

If a customer's normalized email changes after challenge issuance, the old
challenge cannot verify the new email state and returns `VERIFICATION_INVALID`.

## Trusted Verification Authority Integration

Verification success constructs challenge-scoped trusted evidence and calls
`CustomerOrderIdentityService.markEmailVerified` through
`EmailVerificationAuthorityPort`. The service does not directly update
`email_verification_state = VERIFIED`.

## Identity Linking Architecture

`linkExternalIdentity` requires:

- current principal;
- assurance `AUTHENTICATED`;
- persisted customer;
- email state `VERIFIED`;
- trusted `CustomerIdentityBindingAuthorityPort` evidence;
- safe provider subject;
- provider/subject not bound to another customer.

Missing principal, `TEST` principal, unverified customer and missing trusted
provider evidence fail closed. Provider email equality alone is not accepted.

## Account Merge Policy

Account merge is not implemented. Same email, provider email, name or payment
email does not merge customers. Conflicting provider/subject binding returns
`IDENTITY_CONFLICT`.

## Guest Order Claim Architecture

`GuestOrderClaimAuthorityPort` represents future trusted claim evidence. The
default authority fails closed. Synthetic trusted tests can claim an unowned
order through existing immutable `OrderOwnershipBindingAuthorityPort` semantics:
one owner wins, same-owner retry is idempotent and different owner attempts
conflict.

## Claim-By-Email Rule

Verified customer email matching historical order email is not sufficient to
claim ownership. KS-08-02 does not generate retroactive evidence for legacy
orders.

## Rate Limit Architecture

`CustomerRegistrationRateLimitPort` uses hashed limiter identities such as
normalized email hash and optional IP hash. The in-memory implementation is for
local/tests only. Production distributed rate limiting is not ready.

## Audit Behavior

Audit events use safe IDs and reason codes:

- `CUSTOMER_REGISTRATION_REQUESTED`
- `CUSTOMER_EMAIL_VERIFICATION_ISSUED`
- `CUSTOMER_EMAIL_VERIFIED`
- `CUSTOMER_EMAIL_VERIFICATION_FAILED`
- `CUSTOMER_IDENTITY_LINKED`
- `CUSTOMER_IDENTITY_LINK_DENIED`
- `CUSTOMER_ORDER_CLAIM_DENIED`
- `CUSTOMER_ORDER_CLAIMED`

Audit metadata excludes raw email where customer ID is sufficient, raw tokens,
token hashes, provider subjects, provider bearer tokens, session tokens, product
keys, ciphertext and decrypted material.

## Safe Inspect Behavior

Added:

```sh
npm run customer-registration:inspect -- <customerId>
```

The command prints customer ID, verification state, active challenge count, last
challenge creation timestamp and identity binding count. It does not print raw
email, raw verification token, token hash, provider subject, session token or
product-key material.
