## SupplierPort Changes

The existing SupplierPort was refined for a supplier-neutral deficiency: catalog/product/offer returns now expose normalized supplier records with both supplier-side references and explicit mapped KeyCore IDs. This preserves the recognizable existing concepts while preventing supplier IDs from being confused with internal IDs.

Additional capability flags were added for full catalog, price lookup, region evidence, purchase, and health/rate-limit information.

## Capability Model

Capabilities describe behavior only and contain no credentials, endpoint URLs, or transport configuration. Unsupported optional capabilities fail explicitly with `UNSUPPORTED_CAPABILITY`.

## Normalization Model

- `NormalizedSupplierProduct` wraps supplier identity, supplier product ID, mapped product summary, lifecycle and changed timestamp.
- `NormalizedSupplierOffer` wraps supplier identity, supplier offer ID, supplier product relation, mapped offer summary, region evidence, captured timestamp and safe metadata.

## SupplierRegistry Design

`SupplierRegistry` stores adapter references, prevents duplicate `SupplierId` registration, resolves known suppliers, fails unknown lookups with `NOT_FOUND`, and lists identities/capabilities deterministically.

## MockSupplier Behavior

MockSupplier is offline and deterministic. It supports configured synthetic products/offers, full and delta catalog, lookup, price, region evidence, purchase scenarios, reconciliation, key-handle retrieval, refund claims, health/rate-limit metadata and deterministic fault injection.

## Generated Catalog Fixture

`createGeneratedMockSupplierFixtures` supports scalable deterministic fixture creation:

```ts
createGeneratedMockSupplierFixtures({
  productCount: 50_000,
  seed: "keycore-default",
});
```

The generator uses deterministic arithmetic plus a small built-in string hash. It does not use randomness, external libraries, external APIs, real supplier payloads or real commercial catalog data. For the same seed/configuration it produces stable product IDs, offer IDs, titles, order, offers, prices, currencies, availability states and timestamps.

The default large profile creates exactly 50,000 products. Every tenth generated product gets a second deterministic offer, so offer uniqueness is tested separately from product uniqueness.

## Region Scenario Matrix

Generated fixtures deterministically cover:

- Germany-compatible evidence;
- EU-compatible evidence;
- Global-compatible evidence;
- US-only evidence;
- LATAM evidence;
- CIS evidence;
- Asia evidence;
- unknown region;
- contradictory region metadata;
- VPN-required activation;
- foreign-account-required activation.

KS-03-01 still does not implement the final Germany compatibility engine. Unknown and contradictory evidence remains raw structured evidence and review-required.

## Error Taxonomy

The supplier-neutral taxonomy includes authentication, authorization, rate limit, timeout, transient, invalid response, not found, out of stock, rejected, conflict, unsupported capability and unknown categories. Error messages are sanitized and tests assert no credential-like content leaks.

## Idempotency Model

Same idempotency reference plus same semantic purchase request returns the same receipt. Conflicting reuse fails with `CONFLICT`. MockSupplier does not create duplicate supplier purchases for repeats.

## Reconciliation Model

Synthetic reconciliation maps accepted and delayed purchases to resolved results, ambiguous purchases to still ambiguous, and failed/unavailable paths to manual review.

## Fault Injection Model

Faults are opt-in by operation and deterministic:

- `TIMEOUT`
- `RATE_LIMITED`
- `TRANSIENT_ERROR`
- `TERMINAL_ERROR`
- `MALFORMED_RESPONSE_SIMULATION`

## Contract Test Architecture

`runSupplierContractTests` accepts a supplier factory and fixture references. The suite checks identity, contract version, capability consistency, pagination, empty catalog behavior, lookup, money, availability, region evidence, idempotency, reconciliation, key/refund capability behavior, health/rate limits, and secret safety.

## Security and Secret Checks

MockSupplier uses no real supplier credentials, real product keys, payment credentials or production customer data. Key retrieval returns handles only. No network I/O or production supplier adapter was added.

`npm.cmd run check` passed locally, including the secret scan. `npm.cmd audit --audit-level=low` reported 0 vulnerabilities.

## Scale Test Results

After PR #4 hardening, the MockSupplier scale suite verifies:

- generator creates exactly 50,000 products;
- repeated generation with the same seed/config has identical sampled IDs, titles and ordering;
- large-catalog pagination is deterministic for first, middle and last pages;
- generated SupplierProductIds are unique;
- generated SupplierOfferIds are unique;
- generated delta filtering returns deterministic changed records and empty no-change pages;
- all required region scenarios are distributed;
- generated samples contain no credential-like or product-key-like material;
- 50,000-product generation completed under the CI-oriented 15-second test budget locally.

## Runtime and Memory Considerations

The 50,000-product fixture is generated in memory once per scale test group. It is not committed as JSON, logged, snapshotted or regenerated per test. Catalog pagination slices fixture arrays before normalization, and product/offer lookup uses maps to avoid avoidable catalog scans.
