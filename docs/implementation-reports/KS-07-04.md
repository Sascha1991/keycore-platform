## Kinguin Documentation Findings

Official Kinguin documentation was re-checked for Order v2, Order v1, error
codes and return-key behavior.

Verified:

- purchased keys are retrieved through `GET /v2/order/{orderId}/keys`;
- authentication uses `X-Api-Key`;
- the key retrieval endpoint supports `page` and `limit`;
- output is an array of key objects with `id`, `serial`, `type`, `name`,
  `kinguinId`, `offerId` and `productId`;
- `serial` is product-key material;
- order status `processing` means the order is waiting for key delivery;
- order status `completed` means all keys have been delivered;
- key statuses include `PENDING`, `PROCESSING`, `DELIVERED`, `RETURNED`,
  `REFUNDED` and `CANCELED`;
- the docs recommend periodic key download, using `order.status` webhook when
  status becomes `completed`, or polling order details until keys are delivered;
- `POST /v2/order/{orderId}/keys/return` is a separate state-changing return
  operation and is not used by KS-07-04;
- the docs do not state that key download is destructive or one-time.

KS-07-04 therefore models Kinguin key retrieval as repeatable read-only, with
durable local leases and retryable network/rate-limit failures. Malformed key
responses fail closed.

## Fulfillment State Model

Fulfillment states:

- `PENDING`
- `READY`
- `RETRIEVAL_IN_FLIGHT`
- `RETRIEVED`
- `DELIVERY_PENDING`
- `DELIVERED`
- `FAILED_RETRYABLE`
- `FAILED_TERMINAL`
- `AMBIGUOUS`
- `MANUAL_REVIEW_REQUIRED`

Retrieval and delivery are separate. A successfully encrypted supplier key ends
at `DELIVERY_PENDING`; KS-07-04 does not implement production customer email.

## Migration

Added reversible migration:

- `014_secure_key_fulfillment`

Tables:

- `fulfillment_operations`

The schema stores only encrypted secret material and safe metadata. It does not
add plaintext key, raw supplier response, supplier response JSON or
customer-visible key-copy columns.

## Encryption

Algorithm:

- `AES-256-GCM-v1`

Design:

- random data encryption key per secret;
- random 12-byte nonce per secret;
- authentication tag;
- canonical AAD binding fulfillment ID, supplier ID, external supplier order
  ID, purpose, algorithm and version;
- wrapped data encryption key;
- explicit `encryptionKeyId`;
- explicit `encryptionVersion = 1`.

Runtime configuration:

- `KEYCORE_FULFILLMENT_MASTER_KEY`
- `KEYCORE_FULFILLMENT_MASTER_KEY_ID`

The master key must be base64-encoded 32-byte material. Missing or malformed
configuration fails closed. No real key is committed and no production key is
generated silently.

Key rotation readiness is provided by persisted key ID, version and wrapped DEK.
Full rotation workflow remains future work.

## Controlled Retrieval Gates

Preparation command:

```sh
npm run kinguin:prepare-live-key-retrieval -- <controlledProcurementApprovalId>
```

Preparation is DB-only and performs zero supplier key requests.

Execution command:

```sh
npm run kinguin:execute-approved-key-retrieval -- <fulfillmentApprovalId> <oneTimeToken>
```

Execution requires:

- `KEYCORE_ALLOW_KINGUIN_LIVE_KEY_RETRIEVAL=true`;
- `KEYCORE_KINGUIN_CONTROLLED_KEY_RETRIEVAL_MODE=CONTROLLED_VERIFICATION_ONE_TIME`;
- correct unexpired one-time token;
- confirmed controlled procurement;
- known external supplier order ID;
- supplier `kinguin`;
- no existing encrypted secret;
- valid crypto configuration;
- retrieval lease ownership.

The prior read-only and purchase-mutation flags do not enable key retrieval.

## Idempotency And Concurrency

Fulfillment creation is idempotent per controlled procurement approval. The
database enforces one fulfillment operation per controlled approval and one
secret per fulfillment operation.

Retrieval execution uses a durable lease:

- one worker acquires `RETRIEVAL_IN_FLIGHT`;
- concurrent workers receive in-flight state;
- stale retryable retrieval can be reacquired;
- already retrieved fulfillment cannot retrieve again.

## Audit And Outbox Restrictions

Audit and outbox payloads use safe IDs and state only. They exclude plaintext,
ciphertext, nonce, tag, wrapped DEK, master key material, one-time tokens, token
hashes and raw supplier responses.

GitHub Actions initially exposed a PostgreSQL-only fixture defect: fulfillment
operations with a controlled procurement approval ID were inserted without the
referenced `controlled_procurement_approvals` row. The tests were corrected to
create the approval through the real repository before inserting fulfillment
operations. The 50k metadata test was also changed to use PostgreSQL
`generate_series` instead of a large client-side `VALUES` statement, preserving
the same acceptance coverage while avoiding CI timeout risk.
