## Publication State Model

States:

- `NOT_PUBLISHED`
- `PENDING_CREATE`
- `PUBLISHED`
- `PENDING_UPDATE`
- `UNPUBLISH_PENDING`
- `UNPUBLISHED`
- `BLOCKED`
- `FAILED`
- `REVIEW_REQUIRED`

Ambiguous create outcomes, pending creates and local persistence failure after remote create move to reconciliation-required behavior and prevent blind duplicate WooCommerce creation.

PR #10 hardening added explicit transport-ambiguity handling:

- `POST` network disconnects, connection resets, aborts, timeouts and unreadable/truncated responses are classified as `StorefrontAmbiguousError`;
- ambiguous create becomes `RECONCILE_AMBIGUOUS_CREATE` and does not become `FAILED_REMOTE_CREATE`;
- automatic retry after ambiguous create returns reconciliation again and does not issue a second `POST`;
- deterministic HTTP rejection such as auth/client errors remains a normal create failure;
- ambiguous `PUT` update and soft-unpublish become `RECONCILE_AMBIGUOUS_UPDATE` and `RECONCILE_AMBIGUOUS_UNPUBLISH`.

When a remote WooCommerce product is created and the local publication persistence write fails, the service preserves the known remote product ID in the reconciliation record if the repository is available for that reconciliation write. If the repository is completely unavailable, the operation stops and requires operational reconciliation without blind title search or another create.

Audit environment is injected via `StorefrontPublicationServiceOptions.environment` and uses the existing audit environment values: `LOCAL`, `CI`, `STAGING` and `PRODUCTION`. The service does not infer environment from storefront channel or domain.

CI run #33 exposed that `003_catalog_sync_foundation.down.sql` was not fully idempotent when later rollback paths had already removed `supplier_offers` or `supplier_products`. The PR #10 hardening commit makes those down-migration `ALTER TABLE` statements use `IF EXISTS`; it does not change any up migration, uniqueness constraint or storefront publication schema.

## WooCommerce Contract

The WooCommerce adapter is behind `StorefrontPort` and uses documented REST API `wc/v3` product endpoints:

- create: `POST /wp-json/wc/v3/products`;
- read: `GET /wp-json/wc/v3/products/<id>`;
- update: `PUT /wp-json/wc/v3/products/<id>`;
- soft-unpublish: `PUT /wp-json/wc/v3/products/<id>` with draft, hidden catalog visibility and out-of-stock status.

No hard delete endpoint is used.

References:

- [WooCommerce REST API documentation](https://developer.woocommerce.com/docs/apis/rest-api/)
- [WooCommerce products REST API documentation](https://developer.woocommerce.com/docs/apis/rest-api/v3/products/)

## Persistence

Migration `005_storefront_publication` creates durable storefront publication mappings and enforces:

- unique `ProductId + storefront`;
- unique `storefront + remote_product_id` where a remote ID exists;
- foreign-key ownership by `products(id)`;
- checked publication states.

The down migration drops the new indexes and table without rewriting supplier, catalog, order or WooCommerce state.
