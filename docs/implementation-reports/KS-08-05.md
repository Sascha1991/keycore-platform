Foundation as a transport-neutral extension to the existing customer account,
registration and order ownership boundaries. Guest checkout remains allowed,
but Product Key access requires a verified KeyRaNo account. A guest order may be
claimed only with a high-entropy one-time Kaufcode, matching verified account

## Architecture

KS-08-05 adds a claim credential service and persistence adapters without
adding production HTTP, production email, WooCommerce, password login or real
key reveal.

The claim path is:

```text
trusted post-order claim issuance
-> hash-only expiring guest order claim challenge
-> authenticated verified KeyRaNo account
-> claim code consume
-> existing trusted order ownership binding
-> normal owned-order key access path
```

The claim code can resolve the order, while an optional submitted order ID is
only context. `customerId`, checkout email, WooCommerce identity, supplier
order references and order IDs from a request are not authority.

## Claim Credential And Persistence

- Raw Kaufcode generation uses 32 random bytes encoded as base64url by default.
- PostgreSQL and in-memory persistence store only SHA-256 token hashes.
- Challenges are purpose-bound to `GUEST_ORDER_CLAIM`, expiring and single-use.
- Reissue revokes older active challenges for the same order and purpose.
- Definitive delivery failure revokes the newly created challenge.
- PostgreSQL migration 019 adds `keycore_orders.checkout_email_normalized`,
  immutable non-null snapshot enforcement and
  `guest_order_claim_challenges`.
- Down migration removes the table, indexes, trigger/function, constraint and
  column.

## Transport Boundary

`CustomerAccountTransportHandler.claimGuestOrder()` models the future
`POST /v1/customer/orders/claim` contract. It requires authenticated session
resolution, Origin validation, CSRF validation, rate limiting and strict body
validation. It returns no raw claim code and does not decrypt, retrieve, email
or deliver Product Keys.

## Tests

Focused unit coverage verifies:

- trusted claim issuance stores only token hashes;
- Product Keys are not sent in claim email;
- untrusted, owned, missing-email and delivery-failed issuance fail closed;
- delivery failure revokes the new challenge;
- authenticated verified customer with matching email and active code can claim;
- wrong email, missing principal, unverified account, invalid code, replay and
  email-only attempts are denied;
- reissue invalidates older claim codes;
- concurrent consumes produce one ownership bind;
- audit, limiter keys and responses do not expose claim/session/product-key
  markers;
- account transport requires POST-style authenticated Origin/CSRF/rate-limit
  controls.

Focused PostgreSQL coverage verifies:

- claim creation stores hash-only tokens and persists checkout email snapshots;
- concurrent claim consumption produces one successful owner binding;
- consumed/replayed credentials fail closed;
- safe inspect excludes raw email, raw claim code and token hash;
- invalid token hashes are rejected by database constraints.
