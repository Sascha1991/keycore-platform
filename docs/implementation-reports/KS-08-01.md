# KS-08-01 Implementation Report

## Summary

Implemented the customer account backend/application foundation as a
transport-neutral read service. The implementation adds account summary, owned
order history, owned order detail, safe key-vault metadata, invoice metadata,
activation instruction metadata and access audit events.

invoice generation, guest order claim flow, Kinguin key retrieval/purchase or
live Stripe mutation was added.

## Migration

Migration added: NO.

Existing schema from KS-07 already provides `keycore_customers`,
`keycore_orders.customer_id`, immutable order ownership,
`fulfillment_operations.order_id` and encrypted fulfillment metadata. KS-08-01
only adds read projections and does not require a new table.

## Architecture

`CustomerAccountService` accepts a trusted
`AuthenticatedCustomerPrincipal`. It does not accept raw session tokens and
does not use request-supplied `customerId` as authority.

`CustomerAccountReadRepository` is a narrow read repository for:

- account summary;
- owned order history;
- owned order detail.

The PostgreSQL adapter filters owned orders in SQL with
`keycore_orders.customer_id = $principalCustomerId`.

## Account Summary Fields

- `customerId`
- `emailMasked`
- `emailVerificationState`
- `createdAt`

Raw email, provider subject, session ID, token hash and auth context internals
are not exposed.

## Order History Query Strategy

The PostgreSQL query joins `keycore_orders` with safe product title and
fulfillment metadata while filtering by `customer_id` in SQL. Supplier order
IDs and encrypted secret material are not selected.

## Pagination Strategy

- default limit: 20;
- max limit: 100;
- deterministic ordering: `createdAt DESC, orderId DESC`;
- HMAC-signed opaque cursor scoped to the customer ID.

Malformed, tampered or cross-customer cursors return `BAD_REQUEST`.

## Customer-Facing Order State Mapping

- refunded -> `REFUNDED`;
- cancelled -> `CANCELLED`;
- manual review or ambiguous -> `ACTION_REQUIRED`;
- completed/fulfilled -> `COMPLETED`;
- procurement succeeded and fulfillment pending -> `READY`;
- otherwise -> `PROCESSING`.

## Order Detail Authorization

Wrong-customer, unknown and unclaimed legacy orders return the same
`RESOURCE_NOT_AVAILABLE` customer-facing result. Authorization follows:

```text
principal.customerId -> keycore_orders.customer_id -> order -> linked fulfillment metadata
```

## Key Vault Metadata Model

Metadata includes fulfillment ID, key-vault status, delivery status, encrypted
secret presence, retrieved/delivered timestamps and `keyAccessAvailable`.

No plaintext, ciphertext, nonce, tag, wrapped key, delivery capability or
master-key detail is returned.

## keyAccessAvailable Rule

`keyAccessAvailable` is true only when the order is owned by the authenticated
customer, fulfillment is linked to that order, retrieval state is `RETRIEVED`,
fulfillment status is `DELIVERY_PENDING`, delivery state is `PENDING` and an
encrypted secret exists.

Metadata view never decrypts and never calls the delivery port.

## Invoice Metadata Model

Invoice metadata supports `NOT_AVAILABLE`, `PENDING`, `AVAILABLE` and
`FAILED`. KS-08-01 does not invent invoice numbers, tax logic, VAT rules, PDFs,
storage paths or internal document identifiers.

## Activation Instruction Policy

Structured known platform metadata can produce platform instructions. Product
title text alone is non-authoritative and falls back to generic
`NOT_AVAILABLE` behavior.

## Guest/Unclaimed Order Policy

Legacy and unowned orders remain inaccessible. KS-08-01 does not claim orders
by email equality, payment email, provider email, supplier data or historical
fulfillment metadata.

## Access Audit Events

- `CUSTOMER_ACCOUNT_VIEWED`
- `CUSTOMER_ORDER_HISTORY_VIEWED`
- `CUSTOMER_ORDER_VIEWED`
- `CUSTOMER_ORDER_VIEW_DENIED`
- `CUSTOMER_KEY_VAULT_VIEWED`
- `CUSTOMER_INVOICE_METADATA_VIEWED`
- `CUSTOMER_ACTIVATION_INSTRUCTIONS_VIEWED`

Audit metadata contains safe IDs, reason codes and counts only.

## Transport Decision

Transport-neutral only. Future HTTP mappings may use account GET endpoints, but
KS-08-01 adds no HTTP server or frontend.

## Cache Policy

Future account HTTP responses must use `Cache-Control: private, no-store`.
