## Architecture And Safety

No production business module, migration or database constraint changed. The
migration baseline remains 027. Tool credentials are child-process environment
variables, never arguments or evidence. Tool errors become stable safe reason
codes and raw stderr is not emitted. Both databases and the dump are always
removed. No external provider adapter is instantiated.

Initial Quality Gates #166 stopped in the unchanged concurrent guest-claim
integration test before any dedicated Phase-11 suite ran (842 passed, 1 failed).
Because prior KS-11-02 through KS-11-04 artifact uploads used unconditional
`always()`, their skipped suites produced misleading secondary missing-artifact
failures. KS-11-06 adds stable step IDs and archives each artifact only when its
suite was not skipped, matching the existing KS-11-05/06 behavior without
weakening any release gate.

Quality Gates #167 reached the native exercise and exposed a synthetic fixture
timestamp mismatch. Migration 025 creates emergency-control rows at migration
time, while the fixture had assigned an older fixed `updated_at`, correctly
violating `created_at <= updated_at`. The fixture now preserves the migration
`created_at` as its pause time, records matching pause-event times and uses the
actual exercise time for explicit post-restore resumes. No production code,
migration, constraint or recovery invariant was changed.

Quality Gates #168 then exposed an ambiguous `record_version` reference in the
synthetic guest-claim recovery statement because both joined tables define that
column. The update now explicitly targets the challenge alias. Safe row counts
and invariant counts are also collected sequentially so the source `pg.Client`
never receives overlapping queries; this removes the recovery-originated pg@9
deprecation warning without changing what is validated.

Quality Gates #169 attempt 2 reached Redis-loss validation and identified an
incorrect fixture expectation: it required five orders before the fifth,
post-recovery continuation order is intentionally created. The guard now
captures PostgreSQL order count and global-control state immediately before
`FLUSHDB`, then proves both remain identical and paused afterward. This tests
durable-state survival directly and retains the explicit-authority requirement
before creating the continuation order.
