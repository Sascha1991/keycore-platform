## Delivery Model

Delivery is a two-step model:

1. `prepareDelivery` verifies fulfillment readiness and calls
   `CustomerOrderAuthorizationPort`.
2. `executeDelivery` claims the approval, re-authorizes ownership, decrypts only
   at the final delivery boundary, calls the delivery port and ACKs by marking
   both attempt and fulfillment delivered transactionally.

The implemented channels are fake/test/admin-controlled test channels only.
Production customer email and production customer HTTP delivery are out of
scope.

## Authorization Model

The service requires a trusted customer/order authorization port. The
authorization context binds:

- customer ID;
- order ID;
- fulfillment ID;
- purpose `customer-key-delivery`;
- version `1`.

The persisted context fingerprint must match at execution time. A context swap
or unauthorized ownership state fails closed before decryption.

Production identity is not complete because `keycore_orders` does not yet own a
production customer identity column. Live customer delivery therefore remains
disabled until a future task adds the missing production identity boundary.

## TTL And Live Gate

Runtime configuration:

- `KEYCORE_DELIVERY_APPROVAL_TTL_MS`, default `300000`;
- `KEYCORE_DELIVERY_LEASE_STALE_AFTER_MS`, default `60000`;
- `KEYCORE_ALLOW_LIVE_CUSTOMER_KEY_DELIVERY`, default `false`;
- `KEYCORE_CUSTOMER_DELIVERY_PROTECTED_FULFILLMENT_IDS`, comma-separated.

Invalid timing values fail closed. Protected fulfillment IDs are blocked unless
the explicit live customer delivery gate is true.

## Decryption, Crypto And KMS

KS-07-05 reuses KS-07-04 encrypted fulfillment secrets and authenticated
fulfillment encryption context. It does not re-encrypt or migrate existing
secret material.

Plaintext is produced only after successful claim and re-authorization. It is
passed as a mutable buffer to the delivery port and overwritten in a `finally`
block after the attempt finishes. KMS/decryption errors fail closed as
`FAILED_RETRYABLE` with `FULFILLMENT_KEY_MANAGEMENT_FAILED`.

## Concurrency, Idempotency And Recovery

The repository models explicit claim/acknowledge behavior:

- one worker can claim a delivery approval;
- concurrent workers see `IN_FLIGHT`;
- stale in-flight attempts move to `MANUAL_REVIEW_REQUIRED`;
- successful delivery writes fulfillment `DELIVERED`, attempt `DELIVERED` and a
  deduplicated outbox event in one transaction;
- already-delivered fulfillment is not decrypted or delivered again.

Retryable, terminal and ambiguous provider failures are recorded without
silently marking fulfillment delivered. Automatic customer redelivery policy is
not implemented in this task.

## Post-Dispatch Hardening

Review hardening added an explicit post-dispatch boundary. Before the delivery
port reports success, failures keep their existing pre-dispatch classification:
provider retryable failures stay `FAILED_RETRYABLE`, provider rejections stay
`FAILED_TERMINAL`, ambiguous provider outcomes stay `MANUAL_REVIEW_REQUIRED`
and KMS/decryption failures stay `FAILED_RETRYABLE`.

After the delivery port reports definitive success, KeyCore treats any local
failure before durable `DELIVERED` confirmation as possible external delivery:

- returned status: `MANUAL_REVIEW_REQUIRED`;
- returned reason code: `FULFILLMENT_DELIVERY_OUTCOME_UNKNOWN`;
- no blind automatic redelivery is permitted.

This covers both `markDelivered()` returning no persisted row and
`markDelivered()` or transaction commit throwing. If the follow-up
manual-review persistence also throws, the service still returns the same safe
ambiguous/manual-review result to the caller. The original in-flight attempt
remains present; immediate re-entry returns `IN_FLIGHT`, and stale recovery
moves the attempt to `MANUAL_REVIEW_REQUIRED` without calling the delivery port
again.

Plaintext cleanup still runs from the shared `finally` path for successful
delivery, delivery-port exceptions, post-dispatch DB failure and
manual-review-persistence failure.

## Safe Inspect

Added:

```sh
npm run customer-delivery:inspect -- <fulfillmentId>
```

The command reads PostgreSQL only and prints safe metadata. It does not contact
Kinguin or a delivery provider and does not print plaintext, ciphertext, nonce,
authentication tag, wrapped DEK, master key material, token hashes or one-time
capabilities.

## Audit And Outbox

Audit events and outbox payloads contain safe state, IDs, channel, delivery
reference and reason codes only. Product-key material, encrypted bytes and
token material are excluded.
