## Atomic Lock/Order Strategy

PostgreSQL order creation occurs in one transaction:

1. check idempotency;
2. atomically mark the active `price_locks` row `CONSUMED`;
3. insert the internal order;
4. insert transition history;
5. insert transactional outbox intent.

If any step fails, the whole transaction rolls back. A unique index on `keycore_orders.price_lock_id` prevents two distinct orders from owning one single-use lock.

## Idempotency Strategy

Order creation requires an idempotency key. The fingerprint is derived from product ID, price lock ID, quantity, expected amount and expected currency. Same key plus same fingerprint returns the same order. Same key plus changed input returns `ORDER_IDEMPOTENCY_CONFLICT`.

The service rechecks idempotency after lock-consumption races so concurrent same-key retries converge on one logical order.

## Payment Gating

Procurement can move to `PENDING` or `IN_PROGRESS` only when payment status is `CAPTURED`. Unknown, pending, authorized, failed, cancelled or refunded payment states block procurement.

No real Stripe integration, credential or network call was added.

## Risk Gating

Procurement also requires risk status `APPROVED`. `NOT_EVALUATED`, `REVIEW_REQUIRED` and `REJECTED` block procurement.

## Procurement Behavior

Procurement is modeled without real supplier purchase. `AMBIGUOUS` moves to `MANUAL_REVIEW` and reconciliation intent; it does not trigger supplier fallback. `FAILED_RETRYABLE` also avoids automatic cross-supplier fallback.

## External Event Dedupe

`external_event_receipts` deduplicates by provider, external event ID and event type. Same fingerprint is a duplicate; changed fingerprint is `EXTERNAL_EVENT_CONFLICT`.

## Refund Foundation

Refund request moves a completed order to `REFUND_PENDING`. It does not mark the order refunded. Refund success is a later explicit transition.

## Reconciliation

Manual-review and ambiguous procurement paths can emit `order.reconciliation.requested` outbox intent. The foundation creates bounded reconciliation intent only; it does not run infinite retry loops.

## Audit and Outbox

Safe order audit events are enabled through the `ORDER_*` audit prefix. Outbox events are inserted transactionally with order creation or selected transitions.

Payloads include only safe identifiers, status, reason code and correlation ID. They exclude product keys, credentials, raw provider payloads, card data and supplier acquisition cost.
