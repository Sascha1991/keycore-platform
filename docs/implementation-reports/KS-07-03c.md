# KS-07-03c Implementation Report

## Summary

Implemented the controlled first live Kinguin procurement foundation on branch
`feature/ks-07-03c-controlled-live-procurement`.

The implementation prepares the repository for exactly one explicit
human-approved Kinguin `CONTROLLED_VERIFICATION` purchase while keeping normal
customer procurement gates unchanged and leaving real procurement disabled by
default.

## Kinguin Contract Recheck

Official Kinguin eCommerce API documentation was rechecked on August 24, 2026.

Findings:

- production base remains `https://gateway.kinguin.net/esa/api`;
- authentication uses `X-Api-Key`;
- order creation is `POST /v2/order`;
- documented request body contains `products[].productId`, `products[].qty`,
  `products[].price`, optional `products[].keyType`, optional
  `products[].offerId`, and optional `orderExternalId`;
- `orderExternalId` is documented as a custom external reference that should be
  unique, but no strong server-side idempotency guarantee is documented;
- reconciliation/status lookup uses read-only order lookup;
- key retrieval is a separate `/keys` boundary and is not used by KS-07-03c.

## Migration

Added reversible migration `012_controlled_live_procurement`.

It creates `controlled_procurement_approvals` with constraints for:

- mode `CONTROLLED_VERIFICATION`;
- supplier `kinguin`;
- quantity exactly `1`;
- positive current and maximum acquisition amounts;
- current amount not greater than maximum amount;
- uppercase three-letter currency;
- 64-character request fingerprint and token hash;
- valid statuses and dispatch states;
- expiry after creation;
- success requiring external supplier order evidence and response fingerprint;
- no obvious sensitive text in persisted fingerprints or references.

## Approval Model

Approval statuses:

- `PENDING_APPROVAL`
- `APPROVED`
- `CONSUMED`
- `EXPIRED`
- `CANCELLED`
- `PROCUREMENT_CONFIRMED`
- `PROCUREMENT_REJECTED`
- `AMBIGUOUS`
- `MANUAL_REVIEW_REQUIRED`

Dispatch states:

- `NOT_DISPATCHED`
- `CLAIMED`
- `DISPATCH_STARTED`
- `DISPATCH_CONFIRMED`
- `DISPATCH_REJECTED`
- `DISPATCH_AMBIGUOUS`

## TTL Policy

Default approval TTL is `300000` ms, five minutes. Operators can set
`KINGUIN_CONTROLLED_APPROVAL_TTL_MS`. Expired approvals cannot be claimed.

## Token Design

Preparation generates a 32-byte random base64url one-time token and outputs it
once. Persistence stores only `sha256(token)`. Tests verify plaintext token is
not persisted and cannot authorize another approval.

## Atomic Claim

PostgreSQL claim uses one conditional `UPDATE ... RETURNING` over approval ID,
token hash, status `APPROVED`, dispatch state `NOT_DISPATCHED`, and unexpired
state. Ten concurrent claimers produce one `CLAIMED` owner and controlled loser
states when the PostgreSQL service is available.

The in-memory repository mirrors the same contract for unit tests.

## Fingerprint And Price Binding

The request fingerprint includes:

- operation version `KINGUIN_CONTROLLED_LIVE_ORDER_V1`;
- supplier ID `kinguin`;
- SupplierProductId;
- SupplierOfferId;
- quantity `1`;
- currency;
- supplier price minor units;
- `orderExternalId`;
- exact Kinguin order payload identity.

Price is part of the fingerprint for the first live verification. Any price
change requires a new approval. Maximum acquisition amount remains a separate
defense-in-depth limit.

## OrderExternalId

Preparation generates `keycore-liveverify-<uuid>` and persists it in the
approval. Execution reuses the persisted value and never generates a new one.

## Controlled Transport

The controlled mutation transport allows only:

- `POST /v2/order`

It independently pins scheme `https`, host `gateway.kinguin.net`, base path
`/esa/api`, operation path `/v2/order`, POST method and an empty query string.
It blocks other methods, other hosts, other paths, key endpoints and POST
redirects. The default mutation timeout is `10000` ms via
`KINGUIN_CONTROLLED_ORDER_TIMEOUT_MS`. There is no automatic retry.

## Configuration Hardening

The real CLI composition path now invokes the controlled validators before
creating service transports.

- `kinguin:execute-approved-procurement` calls the controlled mutation
  composition path, which calls `validateControlledMutationConfig(env)`.
- `validateControlledMutationConfig(env)` first calls
  `validateControlledReadOnlyConfig(env)`, so live execution also requires
  `KEYCORE_ALLOW_KINGUIN_LIVE_READONLY=true` for its final preflight GETs.
- `kinguin:list-live-test-candidates`, `kinguin:prepare-live-procurement` and
  `kinguin:reconcile-live-procurement` call the read-only composition path,
  which calls `validateControlledReadOnlyConfig(env)`.

The read-only service uses `KinguinLiveReadonlyGuardedTransport` with only GET
capability. For controlled reconciliation, the guard narrowly permits the safe
order-status lookup and continues to block non-GET methods, `/keys` paths,
order mutation and unsafe redirects. A read-only service is constructed with
mutation disabled even if mutation mode is present in the environment.

## Lifecycle Hardening

PostgreSQL approval transitions now use conditional `UPDATE ... RETURNING`
statements with the expected `record_version` and current state. Conflicts
return `null` rather than raw database errors.

Conditional transitions:

- `cancel`: only `PENDING_APPROVAL`/`APPROVED` with `NOT_DISPATCHED`.
- `markDispatchStarted`: only `CONSUMED` with `CLAIMED`.
- ordinary `markConfirmed`: only `CONSUMED` with `DISPATCH_STARTED`.
- reconciliation `markConfirmed`: only explicit `source: "RECONCILIATION"`
  from `AMBIGUOUS` with `DISPATCH_AMBIGUOUS`.
- `markRejected`: only `CONSUMED` with `DISPATCH_STARTED`.
- `markAmbiguous`: only `CONSUMED` with `DISPATCH_STARTED`.
- `markManualReview`: cannot overwrite `PROCUREMENT_CONFIRMED`,
  `PROCUREMENT_REJECTED` or `AMBIGUOUS`.

If dispatch-start evidence cannot be persisted from the claimed state, the
service does not send the supplier POST. Stale writers cannot overwrite newer
terminal confirmation, rejection or ambiguity states.

## Commands

Added:

- `npm run kinguin:list-live-test-candidates`
- `npm run kinguin:prepare-live-procurement`
- `npm run kinguin:execute-approved-procurement`
- `npm run kinguin:reconcile-live-procurement`

Candidate listing and preparation are read-only. Execution requires approval ID
and one-time token. Reconciliation is read-only and never retrieves keys.

## Audit

Safe procurement-prefixed audit events are emitted for preparation, approval,
claim, dispatch start, confirmation, rejection, ambiguity, reconciliation
request and manual review. Metadata contains safe references only and excludes
API keys, execution tokens, raw supplier payloads, product keys and customer
payment data.
