# KS-09-01 Implementation Report

## Summary

Implemented the Fraud Risk Rules & Manual Review Foundation for Phase 09.
The implementation is deterministic, supplier-neutral, payment-provider-neutral
and persistence-backed.

## Existing Semantics Discovered

- Orders already have `riskStatus`: `NOT_EVALUATED`, `APPROVED`,
  `REVIEW_REQUIRED`, `REJECTED`.
- Procurement is already gated by captured payment and approved order risk
  status.
- Order `MANUAL_REVIEW` is shared by multiple safety causes.
- Fulfillment `MANUAL_REVIEW_REQUIRED` is delivery/retrieval ambiguity and is
  not fraud review.
- KS-09-01 keeps these semantics separate and does not rewrite fulfillment or
  procurement behavior.

## Architecture

- `FraudRiskService` loads trusted facts by order ID from a repository.
- Rule evaluation is deterministic and uses stable reason codes.
- Decision precedence is `DENY > REVIEW > ALLOW`.
- Policy version is `KS09_POLICY_V1`.
- Fact snapshots are canonicalized and fingerprinted using SHA-256.
- Persistence keeps immutable evaluation history and exposes the current
  evaluation by latest timestamp/id.
- Repeated evaluation of the same order/policy/fingerprint returns the same
  persisted evaluation.
- Changed facts produce a new evaluation.
- `isFraudCleared(orderId)` is the downstream guard foundation and fails closed.

## Manual Review

- REVIEW decisions open a durable `FRAUD` manual-review case.
- At most one active `FRAUD` case exists per order.
- Resolution requires trusted `FraudManualReviewAuthorityPort`.
- Production default authority fails closed.
- APPROVE clears only the current matching evaluation/fact fingerprint.
- REJECT remains blocked.
- Stale evaluation approval is denied.
- Resolution does not decrypt, deliver, call Kinguin or mutate Stripe.

## Persistence

Migration 020: YES.

Tables:

- `fraud_risk_evaluations`
- `fraud_manual_review_cases`

Constraints:

- decision/status enum checks;
- bounded score;
- non-empty bounded reason-code arrays;
- policy/fingerprint format checks;
- FK to `keycore_orders`;
- FK from cases to evaluations;
- unique evaluation idempotency on `(order_id, policy_version,
fact_fingerprint)`;
- partial unique index for one open `FRAUD` review case per order.

Concurrency strategy:

- PostgreSQL advisory transaction lock by order ID for evaluation/case
  persistence;
- unique constraints/partial unique index as backstop.

## Rules

- `RISK_AMOUNT_VALID`: zero/negative amount -> `DENY`,
  `INVALID_ORDER_AMOUNT`.
- `RISK_ORDER_STATE_VALID`: cancelled/failed/refunded order -> `DENY`,
  `ORDER_STATE_INVALID`.
- `RISK_PAYMENT_CAPTURED`: payment not captured -> `REVIEW`,
  `PAYMENT_NOT_CONFIRMED`.
- `RISK_CUSTOMER_VERIFICATION`: owned unverified customer -> `REVIEW`,
  `CUSTOMER_UNVERIFIED`.
- `RISK_EXISTING_ORDER_RISK_STATUS`: existing review/rejected order risk ->
  `REVIEW`/`DENY`.
- Currency support check: unsupported currency -> `REVIEW`.
- Rule exception guard: thrown rule -> `REVIEW`, `RISK_RULE_EXCEPTION`.
