## Policy Version

`canonical-grouping-v1`

## Evidence Model

Strong verified evidence:

- Steam App ID;
- platform store ID;
- official product ID;
- GTIN, UPC and EAN;
- trusted source plus verified flag.

Supporting evidence:

- normalized title;
- publisher;
- developer;
- release date;
- product type;
- platform;
- edition marker.

Weak/supporting evidence never auto-groups by itself.

## Mapping State Model

Mappings support:

- `UNMATCHED`;
- `AUTO_MATCHED`;
- `MANUAL_MATCHED`;
- `REVIEW_REQUIRED`;
- `REJECTED`;
- `DETACHED`.

Mappings persist decision source, confidence, reason code, policy version, safe evidence snapshot, optional actor/reason and timestamps.

## Manual Override Model

The service supports manual match, detach and reject commands. Manual commands record actor reference and reason and emit audit-safe events. No admin UI was implemented.

## Persistence and Indexes

Migration `004_canonical_product_grouping`:

- adds canonical metadata fields to `products`;
- creates `canonical_product_identifiers`;
- creates `supplier_product_canonical_mappings`;
- adds verified identifier lookup index;
- adds canonical product mapping index;
- adds mapping state index;
- drops `supplier_products_supplier_product_internal_unique` so multiple supplier products can map to one canonical product.

The active KS-05-02 source of truth for grouping decisions is `supplier_product_canonical_mappings`. `supplier_products.product_id` is a compatibility and routing projection maintained from those decisions.

The migration is reversible. Its down migration intentionally does not recreate the legacy `supplier_products(product_id)` unique index, because KS-05-02 permits multiple supplier products to point at one canonical product. Restoring the old index after legitimate grouping data exists would make rollback fail or encourage data-destructive mapping rewrites. The down migration leaves the `supplier_products.product_id` projection intact and does not delete or rewrite supplier-product mappings.

## PR #9 Migration Rollback Correction

GitHub Actions run #28 exposed that migration `004_canonical_product_grouping.down.sql` tried to recreate the old `supplier_products_supplier_product_internal_unique` index. That legacy invariant was made obsolete by KS-05-02's many-to-one canonical grouping model.

The correction removes legacy index recreation from the down migration, documents the rollback invariant, and adds PostgreSQL integration coverage proving:

- two supplier products can share one canonical `ProductId`;
- migration `004` rolls down without restoring the incompatible unique index;
- migration `004` down remains idempotent after a complete schema rollback;
- the `supplier_products.product_id` projection remains intact during rollback;
- migration `004` can be applied again after the rollback without dirtying the test schema.
