## Migration

Added reversible migration `008_price_locks_profitability`.

It creates `price_locks` with positive locked-price, valid-state, positive-version, expiry-ordering and idempotency uniqueness constraints.

## State Model

Price lock states are:

- `ACTIVE`
- `CONSUMED`
- `EXPIRED`
- `INVALIDATED`
- `REPRICE_REQUIRED`
- `BLOCKED`

Validation results are:

- `SAFE`
- `REPRICE_REQUIRED`
- `BLOCKED`
- `EXPIRED`
- `CONSUMED`
- `CONFLICT`

## Lock TTL Model

The service requires explicit `expiresAt` on creation and rejects expired or stale quote inputs. No production TTL was invented.

## Idempotency Strategy

Lock creation requires an idempotency key. The same key with the same non-secret lock fingerprint returns the same logical lock. The same key with changed inputs returns `IDEMPOTENCY_CONFLICT`.

PR #13 hardening moved race-sensitive creation semantics into the repository/database boundary. PostgreSQL now uses `INSERT ... ON CONFLICT (idempotency_key) WHERE idempotency_key IS NOT NULL DO NOTHING RETURNING ...`, then reads the existing lock by idempotency key and compares `idempotency_fingerprint`.

Concurrent same-key/same-fingerprint callers create one row and all resolve to the same `PriceLockId`. Concurrent same-key/different-fingerprint callers create one row and conflicting callers receive `IDEMPOTENCY_CONFLICT`.

The persisted idempotency tuple is atomic. Valid database states are exactly both `idempotency_key` and `idempotency_fingerprint` null, or both present. The service-created path requires an idempotency key; nullable database state is retained only for migration/future compatibility.

## Profitability Validation Behavior

Validation recalculates current pricing for the product and returns `SAFE` only when at least one current `QUOTED` offer proves:

```text
lockedSellPrice - current fully known acquisition cost >= current hard minimum profit
```

The locked price must also satisfy the current hard minimum sell price and currency.

## Multi-Supplier Behavior

The lock is not tied permanently to one supplier before procurement starts. A different current eligible offer may keep the lock `SAFE` if it satisfies hard profitability constraints.

Supplier fallback after ambiguous procurement remains outside this task and remains governed by the routing state machine.

## Consumption Behavior

`consumePriceLock` validates the lock first and then calls repository-level `consumeIfActive(lockId, expectedVersion)`.

## Concurrency Handling

PostgreSQL consumption uses a single conditional update on `id`, `status = ACTIVE`, non-expired state and `record_version`. Concurrent consumers cannot both consume the same lock.

PR #13 hardening also changed status updates to return explicit `UPDATED` or `CONFLICT` repository results. Stale optimistic transitions return the current persisted lock instead of throwing the generic "expected row" persistence error. The service maps current terminal states fail-closed.

## Emergency Stop Behavior

The foundation reuses current pricing enablement. If global pricing or product pricing is disabled, current quotes are blocked and existing active locks fail validation closed.

## Persistence

`PostgresPriceLockRepository` supports create, lookup by ID, lookup by idempotency key, status update and atomic consumption. `InMemoryPriceLockRepository` mirrors the same semantics for unit tests.
