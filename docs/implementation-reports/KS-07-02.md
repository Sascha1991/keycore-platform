# KS-07-02 Implementation Report

## Summary

Implemented the Stripe PaymentIntent foundation for KeyCore checkout orders. The implementation adds local payment reservation and persistence, a Stripe PaymentIntent adapter, raw-body webhook signature verification, safe webhook state handling and documentation. PR #15 hardening added a durable create/recovery lease so crashed or ambiguous PaymentIntent creation does not leave payments permanently stuck.

## Acceptance Criteria Status

- One logical Stripe payment per order: implemented with `(order_id, provider)` uniqueness and transaction-scoped advisory reservation.
- Deterministic Stripe idempotency: implemented as `keycore:payment-intent:create:<OrderId>:v1`.
- Durable create/recovery: implemented with `create_attempt_token` and `create_attempt_started_at` on `order_payments`.
- Stale recovery policy: caller supplies `createLeaseStaleAfterMs`; `.env.example` documents `STRIPE_CREATE_LEASE_STALE_AFTER_MS=60000` for local development.
- No DB transaction across Stripe HTTP: implemented by reserving locally before invoking the provider port.
- No persisted `client_secret`: implemented and tested.
- Raw-body webhook signature verification: implemented through Stripe SDK `constructEvent`.
- Supported webhook events: implemented for succeeded, failed, processing and canceled.
- Success validation before capture: implemented for mapping, amount, currency and metadata order relationship.
- Recovered create validation: implemented for amount, currency, `keycore_order_id` and `keycore_payment_version`.
- Failure, canceled and processing are not procurement eligible: implemented and tested.
- Success does not approve risk or start procurement: implemented and tested.
- Test-mode only configuration: implemented and tested.
- Reversible migration: implemented with migration 010 up/down.

## PR #15 Hardening

- Crash before Stripe call: a retry can claim the unowned `CREATION_PENDING` row and call Stripe with the same deterministic idempotency key.
- Remote success plus local failure: the lease remains bounded; after staleness, another caller repeats the same Stripe create operation with the same key and persists the returned logical PaymentIntent.
- Ambiguous create with no external ID: local status becomes `CREATE_OUTCOME_UNKNOWN`; recovery repeats deterministic create instead of retrieving by unknown ID or searching Stripe.
- Fresh lease: concurrent callers return `PAYMENT_CREATE_IN_FLIGHT` and do not perform independent Stripe create calls.
- Stale lease: a later caller can atomically take over creation after the configured stale threshold.
- Definite rejection: local status becomes `FAILED` and is not automatically retried.
- Webhook before create response: signed webhook is receipted when metadata safely identifies the order, but no capture occurs until authoritative local mapping is established.
- PostgreSQL coverage: migration and repository tests prove single create-lease ownership and unrelated-order concurrency when `KEYCORE_TEST_DATABASE_URL` is available.
