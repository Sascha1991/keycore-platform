## Transport Architecture

The new `CustomerAccountTransportHandler` defines a v1 DTO boundary for future
HTTP, Keyrano storefront or WooCommerce adapter composition:

```text
request cookie/header -> opaque session token -> KS-07-07 session resolver
-> AuthenticatedCustomerPrincipal -> account/registration service -> safe DTO
```

The transport rejects request-supplied authority fields such as `customerId`,
`providerSubject`, `orderOwner`, supplier order IDs, fulfillment references and
delivery capabilities where they do not belong.

## Handler Models

Account handler model:

- `GET` account summary resolves a session before calling account service.
- `GET` owned order history validates bounded query params and opaque cursor
  shape before session resolution.
- `GET` owned order detail validates UUID path params and calls
  `getOwnedOrderDetail`; it does not load arbitrary orders directly.

Registration handler model:

- `POST` registration validates strict body `{ email }`.
- Public success remains `REGISTRATION_ACCEPTED`.
- Existing and new email addresses share the same public response.
- No session is created automatically.

Verification handler model:

- `POST` verification validates strict body `{ verificationToken }`.
- Token is treated as secret input.
- Token is never echoed in responses or audit assertions.
- Invalid, consumed and expired tokens collapse to `VERIFICATION_INVALID`.

Identity-link handler model:

- `POST` identity link requires authenticated session, Origin and CSRF checks.
- Body must be empty.
- Trusted provider evidence remains injected through
  `CustomerIdentityBindingAuthorityPort`.
- Raw browser `providerSubject` is rejected.

## Security Policies

Session extraction/resolution:

- session credential is opaque;
- `customerId` request fields are never accepted as principal source;
- missing, malformed, expired and revoked sessions return
  `AUTHENTICATION_REQUIRED`;
- denied sessions do not call account repositories.

Cookie policy:

- `HttpOnly; Secure; SameSite=Lax; Path=/`;
- no token in URLs;
- no localStorage recommendation.

CSRF policy:

- authenticated mutations reuse the KS-07-08 HMAC double-submit CSRF policy;
- SameSite is not the only mutation defense.

Origin/CORS policy:

- KS-08-03 reuses the KS-07-08 origin normalizer;
- production/staging require configured HTTPS origins;
- local/CI may allow deliberate localhost HTTP;
- wildcard credentialed CORS remains forbidden.

Rate-limit reuse:

- transport uses the KS-07-08-style `AuthenticatedCustomerDeliveryRateLimiter`
  port;
- sensitive limiter outage returns `TEMPORARILY_UNAVAILABLE`;
- in-memory limiter remains local/test only.

Cache and response headers:

- account reads use `Cache-Control: private, no-store`;
- mutations use `Cache-Control: no-store`;
- token-sensitive verification uses `Referrer-Policy: no-referrer`;
- all JSON responses include `X-Content-Type-Options: nosniff`.

Error mapping:

- stable public codes map to 400, 401, 403, 404, 409, 429 and 503;
- internal exceptions, SQL, provider errors and stack traces are not returned.

Request schema strictness:

- mutation bodies are strict;
- dangerous or unknown authority fields are rejected;
- invalid content type, body size, UUID, cursor and limit fail closed.

## WooCommerce Boundary

WooCommerce remains an adapter/client. It is not authoritative for KeyCore
customer identity, order ownership, verification state, key ownership or
delivery authorization.

The documented future adapter contract explicitly denies email-only
authentication, identity linking and order claiming. A future WooCommerce
identity bridge must provide signed/trusted server-side provider evidence and
must not pass arbitrary browser `providerSubject` as proof.

## Key Reveal Linkage

Account order detail may return safe key-vault metadata and
`keyAccessAvailable=true`, but it does not prepare, decrypt, display, deliver or
consume a delivery capability. Future reveal remains:

```text
account order detail -> explicit customer reveal action
-> KS-07-08 authenticated delivery transport
```
